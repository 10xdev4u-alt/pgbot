# int4_identity_column

**Severity:** warn (critical for `int2`) · **Dimension:** risk · **Object identity:** `schema.relation` (see [configuration](../configuration.md)) · **Requires:** —

## What pgbot observed

One or more columns backed by a sequence — an identity column
(`pg_attribute.attidentity IN ('a','d')`) or a `serial`/owned sequence
(a `pg_depend` `'a'` dependency from a sequence to the column) — have a **narrow
integer type**: `int4` (`integer`) or `int2` (`smallint`). pgbot collects these
into `c.Sequences.NarrowIdentity` and reports each as `schema.table.column is
int4 — wraps at 2.1 billion`. This is **structural**: it reads the column type
from the catalog and does not look at the sequence's current value, so it fires on
a freshly-migrated database that has never been inserted into.

## Why it matters

A sequence-backed `int4` column can only ever produce 2.1 billion distinct values;
an `int2` column, 32767. When the sequence reaches that ceiling the next `INSERT`
raises `nextval: reached maximum value of sequence` — a **write outage** for
anything that inserts into the table, with no partial mitigation. The current
`last_value` is irrelevant: a table doing 10k inserts/second crosses 2.1B in under
three years, and the failure arrives all at once. Because the sequence's own
`max_value` reads 2^63, the sibling finding `sequence_exhaustion` (which uses
`last_value`) cannot warn until the table is already most of the way there — by
which point widening the column means rewriting a huge, busy table. Catching it on
the migration PR, while the table is empty, makes the fix free. It is one of the
most common migration mistakes and is invisible to review of the migration file,
which just reads `id serial` or `id int`.

## How to verify it yourself

```sql
-- Sequence-backed int2/int4 columns (identity or serial / owned sequence):
SELECT n.nspname AS schema, c.relname AS "table", a.attname AS "column", t.typname AS type
FROM pg_attribute a
JOIN pg_class c     ON c.oid = a.attrelid AND c.relkind IN ('r', 'p')
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_type t      ON t.oid = a.atttypid
WHERE a.attnum > 0 AND NOT a.attisdropped
  AND t.typname IN ('int2', 'int4')
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND (a.attidentity IN ('a', 'd')
       OR EXISTS (SELECT 1 FROM pg_depend d JOIN pg_class s ON s.oid = d.objid AND s.relkind = 'S'
                  WHERE d.refobjid = a.attrelid AND d.refobjsubid = a.attnum AND d.deptype = 'a'))
ORDER BY 1, 2, 3;
```

## How to fix it

Define identity/serial primary keys as `bigint` from the start (`bigserial`, or
`bigint GENERATED BY DEFAULT AS IDENTITY`). To widen an existing column:

```sql
ALTER TABLE schema.table ALTER COLUMN id TYPE bigint;
```

This is a **full table rewrite** that holds an `ACCESS EXCLUSIVE` lock — cheap on an
empty branch table, expensive on a large production one, which is the whole reason
to catch it before the data arrives. Widen any `int4` **foreign-key columns that
reference this key** in the same change, or the references overflow first.

## When to ignore it

The table is genuinely bounded — a small lookup/enum table that will never approach
2.1 billion rows — or the column is not actually an ever-growing key. Scope the rule
to that table:

```toml
[[ignore]]
finding = "int4_identity_column"
object  = "public.countries"
reason  = "bounded reference table; ~250 rows forever"
expires = "2027-01-01"
```

Do **not** omit `object` — a bare `finding = "int4_identity_column"` mutes the check
for *every* table, so the next unbounded `int` primary key a migration ships slips
through. Scope it to the one relation you've reasoned about.

## What pgbot cannot see

- It sees the **column type**, not your insert rate. It cannot tell you *when* a
  given `int4` will wrap — only that it will. A truly append-only table doing a few
  rows a day may never reach the ceiling; the finding can't distinguish that from a
  high-throughput table.
- It only flags **sequence-backed** columns. A plain `int4` column you populate
  yourself from an external id space is not caught, even if it will overflow.
- It cannot see gaps: `nextval` is consumed on every attempt (including rolled-back
  inserts and cached blocks), so a sequence burns through its range faster than the
  live row count suggests — the real runway is shorter than `count(*)` implies.
